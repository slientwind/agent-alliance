# Temporal 跨进程接管实验

使用四个不同工作流，同时启动在一个专用任务队列。活动的文件写入模拟远端已受理；收据按工作流标识保存，每次“提交”均独立追加、刷新到磁盘。Activity、Worker身份和尝试号另记。这里的文件只用于模拟远端事实。所有记录均为合成标识，无模型调用。正式运行前固定以下判据。

| 条件 | 观察时点 | 预期 |
| --- | --- | --- |
| completed | 服务历史已有 ActivityTaskCompleted，工作流等待人工信号。强制终止首个 Worker 后发信号 | 替代 Worker 推进工作流，外部提交总数1，原 Activity 仅执行一次 |
| blind | 首次写收据后，Worker 未回报成功即被终止。对照活动对每次投递均提交 | 替代 Worker 收到新尝试；收据2条。证明该策略不适合未知结果调用 |
| reconcile | 同样在提交后丢失回执，第二次投递只按原标识查询收据 | 替代 Worker 消费查到的既有结果；收据仍1条。新的 Activity 尝试不等于新的付费提交 |
| opaque | 同样丢失回执，但本项适配器无查询能力 | 替代 Worker 返回“待人工核对”，无第2次提交。检查流程在人工信号前维持运行，取消后结束，保留原收据 |

每项记录工作流历史、两个进程实际执行的活动尝试、外部提交条数和终态。核对信号是实验夹具，生产业务审核仍需权威决定和当前授权。

本次执行范围收敛到可原样运行的上游 reqrespquery 工作流。以下实测只覆盖调度历史，前表四行是平台联调时的故障注入判据，其中外部收据计数仍待实测。样例收到 request 信号后安排大小写转换活动，可按请求 ID 查询结果。预先固定以下独立观察目标。

1. Worker A完成请求A后终止。在没有应用 Worker 时，提交请求B；服务历史应收到信号，活动B尚未完成。
2. 在同一数据库上重启调度服务，Worker B接管。A与B的结果均可查询，活动完成总数为2。历史能区分两个 Worker。
3. 对相同业务请求B用新的CLI调用再发一次信号。检查是否产生额外的活动及结果；保留实际结论，用于判断平台业务幂等责任。
4. Worker B停止后提交取消，先核验服务端接收和未结束状态。再启动 Worker C，核验取消终态和活动总数。
