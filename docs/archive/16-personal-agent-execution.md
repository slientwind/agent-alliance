# 个人 Agent 的工作能力与执行设计

2026 年 11 月 23 日更新 · Agent Alliance 工作能力、Harness 与 Runtime

个人 Agent 可以接下三类委托：交付可核查的成果，在获准的系统里办妥事务，以及持续跟进变化。对 Alliance，今天最有证据的是从指定资料出简报、汇总已验证口径的单表和多表销售数据、按意见修改并交付批准版。

**同一个计算工具可以成功写出 XLSX，同时漏掉一半输入。** 在 11 月 21 日测试的 Alliance 连接器上，东区表的核准额为 30.10，西区表为 60.20。把两份一起传入，生成文件中的合计为 30.10；调换顺序，合计变成 60.20。目标若是汇总两份，正确答案都是 90.30。这个例子揭示了三个独立的设计问题：工具到底处理了哪些数据，模型能否从返回结果察觉缺口，系统又依据什么宣布完成。[连接器实现](../connectors/server.py) · [运行与成果提交](../backend/internal/runtime/runtime.go)

本文用 **harness** 指组织每轮模型决策的软件，包括指令与上下文组装、工具选择、观察反馈、计划调整和停止判断。用 **runtime** 指落实动作的执行层，包括调度、工作区、权限、超时、持久化、恢复与副作用核对。不同项目对这两个词的边界略有差异。本文按责任判断归属：模型下一轮将看到什么，由 harness 决定；某个动作能否执行、是否已经提交，由 runtime 提供可核对的事实。一个进程可以同时承载两者。[OpenAI Agents 架构](https://developers.openai.com/api/docs/guides/agents-api/architecture) · [Temporal 工作流执行](https://docs.temporal.io/workflow-execution)

**给 Alliance 的优先顺序。** 以已修复的两表汇总作为固定流程对照。在已验证的原文检索和金额核算基础上，逐步扩展单个节点的有界模型循环，专门应对列名变化、缺资料和可修正的工具错误。每个内部动作单独关联预算、授权和回执。最后用相同模型与工具做配对实验，决定哪些任务值得使用动态循环、并行或更长上下文。对口径固定的计算，确定性程序仍应承担最终数值计算。

第 1–3 节从用户委托的工作出发，列出成果、完成判据和 Alliance 当前边界。第 3.1–3.3 节用电商售后拆解消息整理、投诉处置和平台沟通，给出能力边界与验收样例。第 4–8 节追踪本地案例、竞品机制、harness、runtime 和实验方法。第 9–14 节逐项核对十一款产品的工作、渠道、交互与执行机制，第 15 节给出同题实验与方案取舍。附录 A–H 保留 6 个热门 GitHub 项目和 5 款商业产品的来源、功能对照及实施路线。文中将本地实测、固定版本源码、厂商披露与 Alliance 设计建议分别标明。商业产品的内部实现和成功率仅在公开材料支持的范围内讨论。

## 实现复验：资料与计算

**11 月 23 日 Agent 建议表头。** 多表汇总遇到缺列时，可在原步骤授权项目模型根据本次表头和字段用途给出对应建议。业务人员可带入建议并保留已选字段。工具在确认重算后独立核对金额和来源，并把实际采用的列写进工作簿。[实现与验收](15-rebuild.md#agent-在原任务中建议汇总字段)

**11 月 23 日多表字段核对。** 汇总工具一次列出多份 CSV 缺少的字段，业务人员确认整批对应后只需授权一次重算。原任务与固定来源版本沿用，工作簿逐份保留实际采用的列。具有唯一同名列时给出提示，业务口径由发起人确认。[流程与验收](15-rebuild.md#多文件字段在原任务一次补正)

**11 月 23 日语义补查。** 当前普通问答可在选词无命中后，用已配置的本地 BGE 补查固定资料版本。真实 Qwen 用补查所得原句回答了客服工单和展架归还的要求，调用仍沿用检索、回答两步。查无依据时，发起人可选择在原运行内补件。项目网页、已发布网页服务和 Open API 均已验证补件交付。后文各阶段的记录保留当时验证的范围。[语义补查与验收](15-rebuild.md#agent-按业务问题补查固定原文) · [问答补件](15-rebuild.md#原文问答在原任务内补件)

**11 月 23 日引文金额核算。** 已接入一种执行期选择。文本 Agent 查得原文后，根据观察选择同币种金额及加法或减法，由本地工具计算；证据不足时提示补件。在网页项目中，成员可在原对话补件后继续同一运行，原步骤、已用额度和原件引用均可核对。计算步骤可单独用，也可接入既有协作和服务。后续已验证发布服务发起人按原调用身份提交补件。通用跨连接器选择、持续任务和真实企业试点仍待实施或验证。[实现与案例](15-rebuild.md#从原文取数并计算) · [已发布服务补件](15-rebuild.md#已发布服务在原运行补件)

## 实现复验：规划与执行轨迹

**11 月 23 日对话规划复验。** 用户可直接提交目标和资料，规划助手针对可用的真实修订推荐原文问答或 CSV 计算。确认后，执行器按固定步骤运行。已在本地模型上观察到三种早期失败：看到附件元数据却要求重复上传，选择了文本能力却遗漏引文核对，单次汇总后额外增加核对调用。分开声明可执行行动、在推荐前过滤不支持的文件组合，并核对最终交付操作，作为当前规划实现的检查项。该次验收止于规划阶段。引文金额核算已有单独的执行期验证，连接独立服务的多轮工具选择仍待开发。[规格与实例证据](15-rebuild.md#普通成员从附件开始规划)

**11 月 23 日原文问答复验。** 同一个文本 Agent 可根据任务提出检索词，读取平台实际命中的片段，再决定作答、要求补充或补查一次。冷链问题在本地 Qwen3-4B 上给出可定位的引文。首轮无引文时直接跳过第二次模型调用。实际调用按步骤记账，并在恢复时重查授权。本文后续关于通用工具循环的设计，仍包括已有引文金额核算以外的计算工具选择、跨工具纠错和更长任务的停止条件。[运行实现与验收边界](15-rebuild.md#同一-agent-按需检索资料)

**11 月 22 日实现复验。** 第 4 节保留初始连接器漏算的实验记录。更新后的受控汇总已用独立计算及实际交付的 XLSX 校验双表合计 90.30、输入版本和排除行，交换输入次序后结果相同。该次复验只覆盖确定性工具。[复验结果](evidence/rebuild-multi-csv/multi-csv-cases.json) · [交付工作簿](evidence/rebuild-multi-csv/multi-csv-workbook.json)

## 1　可以交付哪些知识与制作工作

用户委托的是“下周一开会用的供应商比较表”，而不是“调用检索和表格工具”。评估这种能力要看最终收到的东西：三家供应商是否齐全、报价是否同口径、来源能否打开、缺项是否标明。下表的委托是可用于试用的任务示例；产品公开材料给出相应能力依据，具体任务仍要按右列验收。

| 可以委托的工作 | 一条具体委托 | 交付物与完成判据 |
| --- | --- | --- |
| 调研与决策准备 | 比较三家供应商的价格、交付周期和售后条款，给采购会用 | 带日期、单位及原文出处的对照表，列出缺项和待确认问题；结论能追溯到对应条款 |
| 阅读与资料整理 | 从培训制度和三次会议记录里提取已经确定的安排 | 决定、负责人、截止日期和原文位置清单；“讨论过”和“已决定”分别标注，未指定负责人留空 |
| 数据处理与核对 | 按地区汇总本周已核准销售额，找出未核准和负数记录 | 可打开的 XLSX，包含分组汇总及异常明细；覆盖全部指定输入，结果可独立重算 |
| 写作、排版与改稿 | 用同一批材料给管理层写一页简报，再给新人做培训讲义 | 两份面向不同读者的文件；关键数字和制度版本一致，指定修改落在正确版本 |
| 幻灯片与视觉制作 | 把培训讲义做成五页演示稿，准备一张活动主视觉供选择 | 可预览的 PPTX 或 PNG；逐页检查内容、尺寸与可读性，图片由人看稿确认 |
| 文件与知识库整理 | 按项目归档授权目录内的材料，标出同名异版文件 | 文件索引、变更清单及冲突项；新路径可打开、原件可追溯，冲突项交人处理 |
| 开发与软件验证 | 用样例数据做一个可筛选的小网页，并验证筛选和导出 | 可运行的项目、启动说明和用例结果；从正常入口操作并检查导出的文件内容 |

**怎样把能力写成产品承诺。** 一句“帮我安排出差”至少有四个可独立验收的终点：查到符合预算的班次、整理可选行程、在预订系统建立订单、获准后付款并取得确认。用户可能只委托到第二步。产品应展示实际结束在哪一步、产物在哪里、下一步由谁决定。持续工作则要另外约定何时检查、什么变化值得提醒、用户什么时候可以结束委托。

**首批最有价值的三项委托**是“给这份核准清单出销售表”“把这批材料做成培训讲义”“按这三条意见改稿并交付批准版”。它们分别检验数据正确性、内容可用性和版本一致性，现有仓库已有原件或验收回执。跨系统写入可以从“准备好可审核的草稿”开始，拿到真实连接器与目标系统回执后再把承诺延伸到发送或提交。

## 3.1　电商售后怎样从消息形成案件

**以一件有负责人、有待办事项、能核对处理结果的售后案件为主线。** 假设买家先说“下单两件，只收到一件”，随后补发照片，又说“另一单也还没到”。客服真正要完成的工作包括登记少件投诉、查清第一单的履约情况，以及跟进另一单的物流。聊天线程只有一个，案件可以有两个。同一订单也可能有两个独立问题；关联依据必须细到订单行、包裹和诉求。以下是平台中立的设计示例，时限、赔付和自动回复条件由商家与目标平台的实际规则配置。

| 时点 | Agent 具体做什么 | 留下什么结果 |
| --- | --- | --- |
| 收到消息和照片 | 按渠道消息编号去重，提取“下单两件”“实收一件”“要求补发”等明确表达，将附件连回原话。另一单的物流诉求单独登记。 | 两个待办事项，各有来源、负责人和下一步；买家主张仍待核实。 |
| 核对订单与包裹 | 按店铺、买家和订单范围查订单行、拆包关系、每包件数、物流和仓库记录。若买家有两笔相似订单，只询问能区分它们的信息。 | 分开列出已证实、仅一方陈述、记录冲突及尚缺的事实。签收记录只能证明包裹签收。 |
| 根据证据分流 | 如第二件在另一包且仍在途，给出物流依据并安排跟进；如仓库确认漏装，按有效规则生成补发或退款选项；证据冲突则转人工或按规则补证。 | 附规则版本与理由的处置建议。需要买家选择时保存其选择，需要商家批准时生成待批动作。 |
| 实施和沟通 | 获准后向订单系统创建补发单，用真实单号回复买家；若对方已发起平台争议，同时跟进平台案件。 | 补发单号、买家回复回执、平台案件号分别归档。平台线和补发线可以同时在途。 |
| 跟进直至关闭 | 按承诺复查物流或资金状态，处理平台补证通知。人员接管后显示已有承诺、证据、已执行动作和截止时间。 | 子事项分别结案。若商家承诺“补发并送达”，有补发单号只能进入跟进，送达证据才满足该承诺。 |

**案件中至少要区分四类事实。** 买家或平台说了什么；订单、仓库或物流实际记录了什么；商家同意承担什么；外部系统实际做成了什么。每条事实附来源与时间。若把它们压成一句“少件已处理”，后续就无法判断还能否退款、是否需要回复平台，或哪项承诺已经逾期。

## 3.2　将售后动作注册为可复用能力

能力按“业务动作＋作用对象＋可验证结果”命名。一个动作如果可以独立授权、独立失败、独立重试或被别的流程复用，就值得拆开。消息分类、工单创建、外部发送和资金动作的边界尤其重要。平台适配器负责不同平台的字段与调用方式；上层使用相同的业务动作，并在平台缺少某项接口时返回具体的人工待办。

| 可复用能力 | 输入与产出 | 在哪些场景复用 |
| --- | --- | --- |
| 提取诉求与待办 | 从消息、附件和时间提取原话、问题类型、诉求、缺失字段及优先原因；支持一条消息有多个意图 | 售前询问、催件、投诉、平台来函 |
| 关联或创建案件 | 输入候选订单行、包裹与现有工单，输出关联依据、新案件或待消歧项；重复消息只登记一次 | 同单反复追问、跨渠道补图、同买家多单 |
| 查询与核对事实 | 用获准的业务标识读取事实，输出带来源的时间线、矛盾和证据缺口 | 少件核对、物流延误、退款进度 |
| 匹配规则与拟定方案 | 按店铺、平台、订单条件和生效时间取规则，输出可选方案、金额依据、审批与截止条件 | 补发、部分退款、争议升级 |
| 起草消息与证据材料 | 按对象生成不同草稿。给买家说明下一步；给平台列诉求、时间线、订单行、附件索引和请求事项 | 买家回复、平台申诉、仓库协查 |
| 对外发送或提交 | 接收已审或预授权的内容版本、目标与附件，只投递允许的内容，取得消息号或平台工单号 | 发客户消息、开平台工单、提交补证 |
| 执行业务处置 | 针对订单行及数量创建补发、发起退款等；分别绑定对应权限、业务动作键和回执 | 履约补救、退款、售后换货 |
| 跟踪承诺和结案 | 按下一次检查时间或平台事件更新状态，对超时、拒绝、待补证或需接管的事项分流 | 催件、平台申诉、补发签收、退款到账 |

**以“提交平台补证”为例。** 输入为店铺与平台案件号、当前要求、截止时间、证据清单、可披露字段、获准提交的材料版本。成功返回平台受理编号或可独立查询的受理记录；被拒返回原因；网络中断且是否受理未知时，按原案件查询。若平台只支持人工门户，Agent 交付材料包、入口和待办，等待人员回填受理凭证。商家收到受理编号后仍可处于等待平台裁决状态。

**三种变化进入不同位置。** 更换平台、渠道或凭据，只替换适配器及其能力声明；店铺调整补发条件或审批金额，只更新有版本的规则；从少件投诉改办物流催件，则重组查件、沟通和跟踪动作。这样一个案件可以先由消息处理进入客服队列，再升级为投诉，期间沿用同一事实和动作记录。

## 3.3　怎样验收电商 Agent 的工作能力

| 委托 | 用哪些能力组合 | 可核验的完成条件 |
| --- | --- | --- |
| “整理昨晚所有用户消息，把今天要做的事给我” | 接入消息 → 去重 → 多意图提取 → 关联工单 → 按时限、影响与待处理方分派 | 每条消息可追溯到案件或有明确忽略原因；给出待回复、等买家、等平台和即将到期清单；低置信关联允许人工修正 |
| “处理买家的少件投诉” | 核实订单与包裹 → 核对事实 → 提出处置 → 获取所需确认 → 执行 → 跟进 | 回复说明事实和承诺；补发或退款有独立回执；拒绝或争议留有升级路径；满足承诺后关闭 |
| “联系平台处理这笔争议” | 读取平台要求和期限 → 准备证据包 → 提交 → 轮询或接收回调 → 补证或升级 → 同步裁决 | 规定时间内提交有效材料，有受理凭证；案件区分待补证、审理中、已裁决。裁决若要求退款，退款作为单独事项核对 |
| “催一下这笔物流并回复买家” | 查订单与运单 → 核对最后节点 → 联系承运方或平台 → 告知买家 → 到点复查 | 查询有时间戳，催办有记录，给买家的下一次更新时间可查；承运方无新信息时不虚构送达日 |

**首轮验收用四个反例。** 重放同一条投诉三次，只有一份原始事件和一次有效处置；买家连提两笔订单，事实与回执不得串单；拆成两包且第二包在途，不能把“只收到一件”直接判成仓库漏发；平台受理后响应丢失，再次执行必须先核对原提交，不能重复申诉。指标可用诉求遗漏率、错绑订单率、按期有效提交率、重复处置数和误结案率。按期有效提交率以有截止时间且应提交的案件为分母，以截止前取得有效受理凭证的案件为分子。

**Alliance 的第一条可验收流程。** 先用合成买家消息、两单三包的订单记录和模拟平台建一个售后收件箱，交付“待办清单＋证据时间线＋买家回复草稿＋平台补证草稿”。可复用现有版本审核、负责人、委托授权和远端回执核对。接下来接一个真实平台的只读订单与物流接口验证归单；正式发送、平台提交、退款及补发分别接入和验收。模拟工单跑通只证明工作流可行，真实平台的权限、字段、时限和回执仍需逐项核对。[现有服务入口](../backend/internal/services/services.go) · [运行与回执](../backend/internal/runtime/remote.go) · [现有集成证据](15-rebuild.md)

**模型回路。** 本地内置模型路径的 Message 只有 role 和 content。Generate 发起一次 Chat Completions 请求，设置 max_tokens 为 1800，成功分支读取正文和总 token。ExecuteStep 用 Eino 单个 Lambda 调用绑定的模型、工具或外部 Agent。由此可以定位缺口：当时的节点不能原生把模型提出的工具调用、对应观察和下一次模型决策连续编排起来。外部 A2A Agent 的内部循环由该服务自行实现。[模型适配](../backend/internal/resources/model.go) · [步骤执行](../backend/internal/runtime/runtime.go)

**上下文与错误反馈。** Inputs 逐份拼接资料，累计正文超过约 96 KiB 的检查与资料不可读共用错误；依赖步骤的正文也会拼入下一次调用。连接器能返回 422，Go 工具适配层再将多种失败归为相同说明。设计上应让“超出上下文”“已撤权”“列无效”“提交结果未知”各有可执行的处理方式。工具应该暴露安全、结构化的失败原因，同时给出可选列名或回执查询入口。[输入组装](../backend/internal/knowledge/sources.go) · [工具响应](../backend/internal/resources/tools.go)

## 6　Harness 如何组织一次模型回合

**进入回合。** 将验收条件、授权工具、冻结的输入版本和未解决问题编入任务状态。每轮以稳定的系统指令和工具定义为前缀，随后附上当前目标、已完成项、最近的动作与观察、必要的证据引用。模型上下文保留足以决策的信息；大原件按需读取。预算分别预留工具定义、观察和模型输出空间。压缩时固定保留用户纠正、未决审批、失败路径、资料版本及其来源，成对保留工具调用和结果。每次按引用读取时再核权限。[上下文工程实践](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents) · [当前资料输入](../backend/internal/knowledge/sources.go)

**选择动作。** 提供用途明确、参数有类型、按修订发布的窄工具。模型可提出“查看列名”“汇总指定版本”“核查文件”或“询问币种”等动作。适配层解析供应商工具调用，查验工具名和参数类型；对不支持原生工具调用的端点，按修订启用经验证的结构化输出适配。解析失败只给一次有限的修正机会。计划只记录依赖和待验条件；列名变化可在原范围重排工作，更换数据集或提升预算需回到外层授权。[现有模型协议](../backend/internal/resources/model.go) · [OpenManus 工具定义及动作处理](https://github.com/FoundationAgents/OpenManus/blob/3309bf4e416fb1c74b008f3e86494439a31bad53/app/agent/toolcall.py)

**回写观察。** 每次动作返回调用 ID、状态、已处理的对象版本、可复核数值、成果引用，以及必要的错误信息。东区工具返回“处理 east:v1，金额 30.10，核准行 1”，harness 对照目标清单，发现 west:v1 仍待处理。若工具只返回“生成成功”，无法做这次比较。对缺列，给实际列名和缺失字段；对网络响应丢失，交给 runtime 查回执。错误反馈的内容决定模型是否有机会换一条有效路径。

**停止与验证。** 模型可以提请完成；独立验证器负责重新打开成果，核对输入覆盖、分组、筛选及合计。验证未通过，只返还缺口和对应证据，再给一次或有限次修正机会。成功、需人输入、无进展、额度耗尽和取消使用不同终态。无进展检测以“同一动作和参数、同一观察、任务状态没有变化”为依据；两份不同文件同名列的读取属于合理重复。最终交付仍走现有业务审核。[Agent 评测中的环境结果](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

**模型与分工。** 固定汇总直接走计算工具。需要解释字段映射时才调用模型；可并行的独立资料可分派只读子任务，分配输入、可用工具、费用与结果格式，汇总器按输入清单逐项验收。父任务保留共享写入权。分别记录模型修订、推理预算、工具集和每回合 token，以便在同一 harness 上评估模型路由，并发现并行是否只增加了费用。[多 Agent 调研系统的实践与成本](https://www.anthropic.com/research/multi-agent-research-system)

## 7　Runtime 怎样执行与恢复动作

**职责分配。** 保留现有 Temporal 方案调度。建议给需要观察反馈的节点增加逐回合活动，工作流决定下一个已记录的状态转移，模型请求和工具 I/O 发生在活动中。PostgreSQL 记业务事实及授权，版本化对象保存原始观察和成果。Temporal 历史只携带必要的标识与小结果。模型响应一旦落账，重放可读取原决策。运行恢复后先重核授权、输入版本和预算。[现有 DAG 与调用意图](../backend/internal/runtime/runtime.go) · [Temporal 工作流](https://docs.temporal.io/workflow-execution) · [活动执行](https://docs.temporal.io/activity-execution)

| 运行时责任 | 建议实现与恢复语义 | 避免的用户可见问题 |
| --- | --- | --- |
| 调度与唯一所有者 | 区分任务、步骤、回合、逻辑动作和尝试。租约配递增代次，迟到回写先比较代次；每个动作保留稳定键。 | 两个 Worker 同时恢复，或旧结果覆盖新决定。 |
| 权限与执行环境 | 工具声明读写范围、允许的网络目标及设备依赖。按任务分配临时目录、限定 CPU／内存／时限；凭据只交给适配器。 | 读错项目文件、脚本长期占用 Worker、本机离线却被记成成功。 |
| 持久化与预算 | 派发前在同一事务写意图并预占；结果与回执落账后再推进。为模型、工具和分支分配统一父预算，按实际尝试与供应商规则核销。 | 重启后丢失工作，重复预占，或并行子项共同超出预算。 |
| 重试与对账 | 明确区分未派发、已拒绝、已成功、提交未知。读操作限次退避；可幂等写入按原键查询或重试；无证明的写入等待对账。 | 网络抖动造成重复外发，或把可修正的输入问题永久挂起。 |
| 暂停与取消 | 等人时释放 Worker，计量等待时长；恢复信号绑定事件和参数摘要。取消阻止新动作，分别记录远端取消请求与最终回执。 | 旧批准作用到新收件人，把本地取消误报成远端已撤回。 |
| 隔离与清理 | 原件只读，新成果单独版本化。浏览器、桌面或子进程保留环境标识和到期时间；清理后从已验证文件或业务回执恢复。 | 重开设备丢失唯一证据，或恢复工作区时误认为外部写入已撤销。 |

**最难的中断发生在对方已受理、本地未记账之间。** 发信示例中先写原动作键和目标摘要，再派发；响应丢失后查同一供应商回执。若供应商既不接受幂等键也不提供查询，本地账本无法证明是否送达，应标明“结果未知”并保留人工核对路径。若收到迟到成功回执，可登记在原动作下，对当前计划是否继续另行校验。现有 A2A 核对逻辑已经能跟进原任务编号，可复用其思路；外部写入本身的一次性仍取决于连接器契约。[远端任务核对与租约](../backend/internal/runtime/remote.go)

**观测。** 记录每轮采用的资料版本、工具修订、动作／尝试标识、非敏感观察摘要、验证结果、费用与阻塞原因。分开统计模型等待、工具执行、队列等待与人工等待。对单次错误交付，应能回答是“模型没有选西区表”“工具只读了首份”“西区结果晚到”还是“验证器漏查”。诊断只需动作与证据元数据，原件沿用项目访问控制。

## 8　怎样测出哪个机制真的有效

**先建立三个基线。** B0 记录当前固定节点的行为。B1 只修工具的输入覆盖契约并增加确定性总额校验，仍按固定流程执行。B2 与 B1 共享相同工具、验证器和预算，增加能观察、调整和重试的 harness。B1 对 B0 衡量工具改进，B2 对 B1 衡量自主循环在变体任务上的增益。对于无需模型的固定计算，另报零模型调用基线。以下均为实验设计，本轮实测限于第 4 节四组连接器输入。

| 单独改变的机制 | 固定条件与故障输入 | 主要观察指标 |
| --- | --- | --- |
| 工具选择与反馈 | 同一模型、工具集与预算；返回“输入错误”或返回缺失列及实际列名。变体包含可确定映射和须人解释两类。 | 无需纠错完成率、错误猜测列名率、无效重试和多余追问数 |
| 上下文构造 | 同一检索语料与任务；全文拼接对照版本引用加按需读取。在上下文中段插入一次口径更正，并强制到达压缩阈值。 | 更正保留率、引用可回查率、输入 token、总费用 |
| 终止与独立验证 | 保持模型、数据和工具一致；分别用模型自报完成和重新读取 XLSX 的验证器，注入遗漏西区表的结果。 | 错误完成率、正确拦截率、误拦正确成果数 |
| 动作持久化与恢复 | 使用同一受控外部服务，分别在派发前、受理后落账前、落账后推进前停止 Worker；另测两 Worker 争抢。 | 原任务恢复率、外部真实写入次数、未知结果误判数 |
| 并行与资源配额 | 同一组十份资料和父预算，对照串行及有限并行；一份慢、一份需重试，另设共享写入冲突。 | 覆盖完整率、慢分支对总耗时的影响、每次成功交付成本 |
| 模型路由与推理预算 | 固定 harness、工具、输入、采样参数；一次只改变模型修订或推理预算，在固定口径与歧义任务上分层。 | 每类任务正确率、首次有效动作耗时、每次成功交付费用 |

**判定方法。** 每个任务用同一套输入做配对试验，保存模型与工具修订、提示版本、输入顺序、固定口径和判分程序。先用受控模型验证状态机，再用真实模型重复运行并报告每组分子、分母、差值和失败轨迹；小样本只用于定位问题。成功由目标环境和文件内容判定。错误完成率以“被系统标记完成的任务”为分母；每次成功交付费用以全批次费用除以通过验收的任务数，同时报告通过率，零成功单列。等待用户时间与实际运算时间分别计量。[评测设计依据](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

**第一项设计决策。** 先为 aggregate 定义支持的输入基数、已处理版本与校验接口，并把双 CSV 顺序交换纳入回归。以 B1 得到可信基线后，再用列名变化、需补币种、压缩后忘记筛选条件三个变体决定是否启用动态 harness。runtime 首先验证恢复时的外部实际写入次数。这样一次效果变化都有可以解释和复现的原因。

### OpenClaw：消息路由决定谁能看到历史

**可委托的工作与入口。** 在 Slack、WhatsApp、Telegram 等既有对话里委托工作，由常驻 Gateway 把消息交给相应 Agent。适合把“从这个团队的资料起草下周简报”留在原频道跟进。管理者配置渠道账号与会话绑定，业务人员从熟悉的对话发起；切换账号、私聊或群组会影响路由。同一名称出现在两个群里不足以证明用户在延续同一项业务。[固定版本项目说明](https://github.com/openclaw/openclaw/blob/6e113fecbf30fdc33caae336139dc785b6dc1489/README.md) · [渠道与 Agent 绑定](https://docs.openclaw.ai/concepts/agent-bindings)

**回合、接管与扩展。** Agent 持有自己的工作目录、会话和工具配置。管理员可将不同 Agent 绑定至不同渠道或会话，再用工具策略约束可用操作。执行主机上的命令另有审批规则，询问无法到达时由审批回退策略决定。多入口共用网关让用户容易找到助手，但模型对话连续、凭据归属和业务任务连续需要分别证明。公开配置能解释报文走向，无法证明企业新成员自动获得旧任务审批权。[多 Agent 路由](https://docs.openclaw.ai/multi-agent) · [执行审批](https://docs.openclaw.ai/tools/exec-approvals)

**设计取舍。** 同一飞书群可讨论多个项目。保存来源账号、会话、消息和显式任务关联；两项工作都可能匹配时展示有权查看的候选标题。接管命令必须命中一个具体待办，通知送不出去时保留网页入口及待办负责人。

### Hermes Agent：把工作委派出去之后谁负责

**可委托的工作与入口。** 可从 CLI 或消息渠道发起调研，将独立主题分给子 Agent，或定义周期作业，把结果递送到指定渠道。用户可在父对话收到后台子任务的命令审批；API 或 webhook 等入口在没有可用审批渠道时，文档描述的是明确拒绝。对于“每天整理一次供应商变更”，要分别知道这轮是否运行、摘要是否形成、目标渠道是否收到。[项目与入口](https://github.com/NousResearch/hermes-agent/blob/2de9f51b8008a7d49a49221c184f2f11cbfc4af1/README.md) · [委派与审批返回点](https://hermes-agent.nousresearch.com/docs/user-guide/features/delegation)

**执行与扩展。** 父任务可指定子任务输出模式，父侧校验；纠正后仍不合规时可留下完成状态和未通过校验的原文。子进程的后台命令随其所有者结束而清理。周期作业另记运行与递送结果，包括作业执行成功而递送失败。用户能用技能和定时配置复用做法，这些资料没有给出任意企业远端 Agent 的统一验收记录。[子任务结果契约](https://hermes-agent.nousresearch.com/docs/user-guide/features/delegation) · [周期与投递状态](https://hermes-agent.nousresearch.com/docs/developer-guide/cron-internals)

**设计取舍。** 子任务返回、结构校验通过、业务验收通过、用户收到通知是四个可独立核对的事实。研究简报已经审核、提醒发送失败时，只补发通知。子任务引用失效时，仅重做对应的资料核验。

### OpenManus：终端内求助与停止检测

**工作与交互。** 开发者配置模型后从主命令输入任务，Agent 可编辑文件、运行 Python、向人提问或结束；项目另提供 MCP 和实验性多 Agent 流程入口。准备一份本地分析文件时，用户可以跟随终端中的工具过程并回答问题。固定版本 AskHuman 调用标准输入，调用进程需要能接到答复。部署成无人值守服务时，业务待办的收件人、超时和恢复点要由宿主提供。[项目启动路径](https://github.com/FoundationAgents/OpenManus/blob/3309bf4e416fb1c74b008f3e86494439a31bad53/README.md) · [人工求助实现](https://github.com/FoundationAgents/OpenManus/blob/3309bf4e416fb1c74b008f3e86494439a31bad53/app/tool/ask_human.py)

**回合与小实验。** 通用 Agent 的步数上限为 20；基类每步检查最近正文与历史助手正文的重复，检测到后追加改换策略的提示。11 月 23 日取该提交的 is_stuck 函数，以阈值 2 和同一检索工具、同一参数构造三条助手消息。三次相同非空正文返回真；三种不同措辞返回假；三次空正文也返回假。只执行了原函数，使用合成消息，未启动模型、工具或完整应用。这给出了“相同操作反复消耗预算却没有新证据”的最小反例。[循环与检测函数](https://github.com/FoundationAgents/OpenManus/blob/3309bf4e416fb1c74b008f3e86494439a31bad53/app/agent/base.py#L170) · [通用 Agent 工具与上限](https://github.com/FoundationAgents/OpenManus/blob/3309bf4e416fb1c74b008f3e86494439a31bad53/app/agent/manus.py)

### nanobot：话题、文件和长期记忆的边界

**工作与交互。** 在 WebUI 为话题选定项目目录，附文件或引用可访问的主机路径，要求修改或整理文件。用户能展开工具活动、文件差异和用量，预览改动，从旧回复分叉；聊天应用可从网页配对，自动化另有管理入口。分叉适合试两种报告写法；如果工具已改写共享目录，仍需检查实际文件版本。[固定版本工作区手册](https://github.com/HKUDS/nanobot/blob/db0306b404954e48ffb82ceae70cbf6f73094348/docs/webui.md) · [自动化手册](https://github.com/HKUDS/nanobot/blob/db0306b404954e48ffb82ceae70cbf6f73094348/docs/automations.md)

**运行与扩展。** 架构将消息总线、会话与上下文、模型工具循环和渠道递送分开。WebUI 可启用封装技能或 MCP 的本地插件，也能选 CLI 应用。各话题保留独立历史、目录及自动化关联；官方说明不同话题仍可能共用长期记忆，严格分隔客户应使用独立实例。没有从该机制推出部门级数据隔离。[运行职责与源码索引](https://github.com/HKUDS/nanobot/blob/db0306b404954e48ffb82ceae70cbf6f73094348/docs/architecture.md) · [目录、记忆与插件](https://github.com/HKUDS/nanobot/blob/db0306b404954e48ffb82ceae70cbf6f73094348/docs/webui.md)

**设计取舍。** 成员默认看原件、差异和待核问题。维护者按权展开调用摘要。复用某次工作时要显式选择模板、获准资料和示例；复制整段历史会把另一个项目的输入与权限一起带入。

## 11　逐产品复核：成员如何配置一个助手

### CowAgent：从业务群进入多角色工作区

**工作、渠道和交互。** 同一实例可接 Web、微信、飞书、钉钉等渠道。成员可从对话发起资料检索、文件整理或定时任务，在 Web 控制台连接渠道、安装技能。团队模式允许在共享对话中组织有不同角色、知识与技能的 Agent。项目也明确支持用自然语言创建技能。这提供了一条“从一次重复任务提炼做法”的构建路径。各 IM 是否支持同等的配置、审批及大文件交付应按渠道单验。[固定版本说明与渠道列表](https://github.com/zhayujie/CowAgent/blob/51ffe5a8df75295a5c063d5bc32a055c643a2599/README.md) · [团队设置](https://docs.cowagent.ai/multi-agent/team)

**运行与治理。** 核心按当前上下文、模型、知识、工具和技能推进计划；会话可绑定项目目录，读写和命令在该目录工作。会话级目录与 Agent 的默认记忆及技能是两套范围；创建团队后成员各有自己的规则、记忆和输出。系统也提供只读、工作区可写等权限档。长期知识和对话空闲后提炼技能会影响下一次执行，应单独定义何时采用、何人可见。[体系结构与数据归属](https://docs.cowagent.ai/intro/architecture) · [技能机制](https://docs.cowagent.ai/skills/index)

**设计取舍。** 企业成员可在任务内把验证过的做法存为 Agent 草稿，指定维护团队并挑选可共享样例。原项目的附件、记忆和凭据各自有归属；发布前重跑样例并固定依赖，后续改进另建修订。

### QwenPaw：收件箱如何收敛多个 Agent 的待办

**工作、渠道和交互。** Console 可管理多 Agent 对话、自动任务、心跳与新邮件处理。Console 渠道对话里触发的审批同时出现在会话与收件箱，可批准、拒绝或取消任务，超时默认拒绝。定时或心跳结果可送收件箱。对新邮件，首次启动监听建立 UID 基线，后续事件与执行摘要、工具记录关联。可由此区分“从今天起处理”和“补扫全部历史”。其他聊天渠道的审批等价性需独立核对。[固定版本 Console 文档](https://github.com/agentscope-ai/QwenPaw/blob/b02e17b8cf3fdde484f33c6981321280a0417232/website/public/docs/console.en.md)

**运行与扩展。** 通道、记忆等可由插件扩展；工具策略、敏感文件保护和沙箱分层。导入配置要先选目标 Agent，再选技能、MCP 等内容，插件默认不选，导入后检查启用状态与计划。其 ACP 对接和 SDK 给出扩展入口，协议名和资料导入均无法证明能作为 Alliance 的 A2A 远端通过异步补件、撤销与交付测试。[项目说明](https://github.com/agentscope-ai/QwenPaw/blob/b02e17b8cf3fdde484f33c6981321280a0417232/README.md) · [插件 SDK](https://github.com/agentscope-ai/QwenPaw/blob/b02e17b8cf3fdde484f33c6981321280a0417232/website/public/docs/plugins.en.md) · [安全机制](https://github.com/agentscope-ai/QwenPaw/blob/b02e17b8cf3fdde484f33c6981321280a0417232/website/public/docs/security.en.md)

**设计取舍。** 会话卡和「我的待办」引用同一决定。定时监听将起点、时区、是否回填和接收方作为委托内容，历史回填另行预览工作量。到期待办显示本次实际处置和重新申请入口。

## 12　逐产品复核：云端工作怎样回到人手里

### ChatGPT Work：访问网站、登录与批准动作

**工作、入口和接管。** 用户从符合条件的 Web、移动或桌面入口交付调研、制作表格或准备预约等任务。云浏览器有独立登录会话；需要认证时，用户接管登录再交还控制。站点访问策略与预约、付款等重要动作的最终确认各有作用。登录可持续到过期，设备上已登录不能直接推定云端有权访问。适合分析“我同意读报价”和“我同意提交采购”这两次决定。[Work 的工作与渠道](https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex) · [云浏览器接管与确认](https://help.openai.com/en/articles/20001280-using-cloud-browser-in-chatgpt)

**运行与构建。** 官方披露了浏览器会话边界、周期任务及工作区技能管理。在提供此能力的工作区，管理员可查看技能所有者、访问范围、使用情况并转移所有权。可重复操作程序、当前用户授权、具体任务的最终确认各有生命周期。公开帮助没有给出浏览器动作幂等键、断线后外部写入重试算法或通用第三方 Agent 协议。[组织技能管理](https://help.openai.com/en/articles/20001066-skills-in-chatgpt) · [周期任务](https://help.openai.com/en/articles/10291617-scheduled-tasks-in-chatgpt)

**设计取舍。** 凭据配置交管理员，按项目读取原件、发布能力和审批当前成果各走独立授权。遇到认证失效时写清由哪个账号负责人处理、恢复哪一步；普通成员和审批者都无须把凭据粘进对话。

### Claude Cowork：手机能跟进什么，取决于资料在哪里

**工作与接力。** 官方示例包括整理文件、从资料制作报告和跨应用协作。符合条件的用户可从 Web、桌面和手机接续云任务；远程使用本机文件、本地连接器或电脑操作时依赖桌面应用及已连接目录。文档须按套餐阅读，个人 Pro、Max、Ultra 的云任务规则不能直接套用到全部企业部署。员工从手机交待“整理报价”，可以跟进任务，却仍可能需要另一台开着桌面客户端的电脑提供报价原件。[任务与示例](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork) · [端侧能力与运行位置](https://support.claude.com/en/articles/15520349-use-claude-cowork-on-web-desktop-and-mobile)

**工具选择与扩展。** Cowork 可按连接器、浏览器、电脑交互的可用性完成工作。插件可携带技能、命令或本地 MCP；其本地 MCP 服务在 Cowork 和 Claude Code 中运行，普通聊天的执行面不同。账户安装、组织分发、运行时设备和资源可达是四种条件。公开材料未建立用户离线时本机资料始终可读或任意远端 Agent 已受组织验证的结论。[电脑使用与工具选择](https://support.claude.com/en/articles/14128542-let-claude-use-your-computer-in-cowork) · [插件分发与本机限制](https://support.claude.com/en/articles/13837440-use-plugins-in-claude)

**设计取舍。** 选能力时解释「需已连接的数据源」；运行时分别展示「已授权但设备离线」「访问已撤回」「原件缺失」。恢复连接、请求授权、提交其他原件是三种不同动作，替代原件要经负责人确认。

## 13　逐产品复核：并行工作如何汇成可核查的交付

### Manus：区分提问、确认、受理和完成

**工作与交互。** 用户可委托批量研究；当系统判断对象可独立处理时，Wide Research 自动拆分。产品界面服务委托者，开发者可以通过任务 API 和 webhook 将进度接回自己的应用。被问“选择哪家供应商”时需要回答问题；若待处理的是一项外部操作，则按该事件公布的输入模式确认。回调通知 ID、问题事件 ID 和任务 ID 分别标识递送、交互和整项工作。[Wide Research](https://help.manus.im/en/articles/11960169-what-is-wide-research) · [任务回调](https://open.manus.im/docs/v2/webhooks-overview)

**协议与运行。** 文档明确：准备工具可显示成功但目标动作仍待确认；确认响应为 confirmed=false 时，输入未被该事件消费，任务仍在等待。邮件示例甚至区分批准保存为草稿与批准发送。开发者可按任务生命周期读取状态和消息；这证明该供应商提供可编程的远端工作接口，无法据此推出它允许注册其他厂商的任意 Agent。内部执行恢复和实际送达质量仍需黑盒试验。[确认事件与输入](https://open.manus.im/docs/v2/task-lifecycle/confirmation-events) · [任务生命周期](https://open.manus.im/docs/v2/task-lifecycle)

**设计取舍。** 外部接入保存原任务引用、请求动作、回调通知、当前等待和结果版本。收到通知后仍要核对它指向哪个待办；HTTP 成功只代表传输。确认页明确显示将批准的对象及效果，草稿获批时只推进内部审核。

### Kimi Agent：并行调研交付哪些东西

**工作与渠道。** 用户从 Web 或移动／平板 App 进入支持的 Swarm 模式，可一次委托多对象资料收集、比较和文件制作。进行中能查看任务拆解、分支进展、来源网站和阶段结果；完成后可收到表格、文档、中间文件夹或代码项目。网站制作还支持多轮修订与导出。套餐及额度会影响可用模式。这里核到的是产品入口与成果形态，未核到同一功能可由第三方企业平台按任务 API 接管。[Swarm 操作与成果](https://www.kimi.com/en/help/agent/agent-swarm) · [Agent 与网站交付限制](https://www.kimi.com/en/help/agent/agent-features-and-limits)

**执行边界。** 厂商描述主 Agent 自主拆分和分派，分支取回资料后汇总。长任务的指令、工具记录、结果和输出共用上下文容量；并行任务按复杂度及分支数消耗共享额度。发布的规模说明不能回答“十家供应商是否都查到有效报价”，也没有公开逐分支账本、恢复保证或可注册的外部 Agent 契约。[Swarm 机制](https://www.kimi.com/en/help/agent/agent-swarm) · [额度与计费](https://www.kimi.com/en/help/agent/agent-quota-and-billing)

**设计取舍。** 用业务对象显示进展，例如「10 家中 8 家有可定位的报价，1 家缺日期，1 家未返回」。用户能先看 8 份证据；是否允许部分交付由原委托决定。父步骤合并前按预期对象清单核对来源、缺项和剩余预算。

## 14　逐产品复核：长期委托中的记忆和授权

### Meta Muse：离开对话后如何保留控制权

**工作与入口。** Meta 披露，用户可在 Muse 应用或 WhatsApp 告知长期目标，让系统跟进事项、结合服务信息准备行动，需要时回到对话请求决定。适合用“持续留意一项申请，变化时通知我”理解目标、监听和提醒的分工。用户可调整可访问的服务。渠道与上市范围以官方发布为限；本次没有逐地区、逐渠道验证操作卡和企业管理员功能。[发布与委托示例](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/)

**技术披露。** 每位用户拥有专用云虚拟机和浏览器；工程说明将 harness 隔离，实际凭据与其分离，对外操作另经 Sentinel 检查。文中提及子 Agent、自建工具和后台工作；这些是其个人助手的实现说明。尚无本研究可核对的组织成员构建、版本发布和第三方远端准入契约，亦未验证隔离机制的实际有效率。[工程团队对隔离与凭据的说明](https://muse.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)

**设计取舍。** 企业长期委托应能回答「谁授权、读哪些对象、从什么时候起、到何时停止、费用记给谁」。负责人离职或撤回授权时，下一轮应能解释为何停止。可复用偏好须有归属、可查可撤；项目内业务事实以获准证据为准。

### 怎样使用这些证据

**接入评估要问两个方向。** Manus 的公开工作接口足以设计“本平台调用它”的适配试验；CowAgent 的技能、QwenPaw 的插件和 Work 的工作区技能支持研究“在其环境内配置能力”。两类证据都很有价值，但前者需要测任务生命周期、后者需要测依赖与发布治理。对于只披露交互的产品，内部检查点、租户隔离和恢复能力保留未知。采购决策还需租户试用、用量账单、原件与真实回执。

**执行信号也要分层。** OpenManus 的重复正文、Hermes 的子任务返回、Manus 的确认响应分别发生在模型回合、编排和外部交互层。企业成员最关心的是「证据够不够，接下来需要谁」。因此由工具声明覆盖，由校验器核实成果，由当前负责人处理缺口，再由发起人或审核人采纳相应版本。

## 15　用同一项企业工作检验设计

以下是根据公开行为设计的对照题。它们把输入、预期动作、故障和裁判先固定，后续可用于竞品账号实测及 Alliance 版本验收。本轮未在十一款产品上运行这些题。

| 相同输入与预期交付 | 用哪些样本做对照，观察什么 | 判分依据和失败信号 |
| --- | --- | --- |
| 采购。A、B、C 三份供应商报价，B 缺有效期，C 与 A 文件同名。交对照表与一份待询问题草稿。 | Kimi／Manus 的并行收集对照 OpenManus 的顺序工具回合；Cowork 对照设备离线后如何补原件。 | 独立标准答案预列三条来源、币种及有效期。B 必须显式缺项，C 可溯源；询价草稿未经发送。记录漏项、返工、实际费用。 |
| 培训。旧制度和已批准新版并存，用户在手机补一条纠正，交讲义与测验。 | nanobot 的文件差异、CowAgent 的项目工作区、Work 的可复用技能及 QwenPaw 双入口审批分别检验修订与资料边界。 | 讲义和答案只引用有效版；原任务保留补充意见；审核后提交旧卡只返回现状。两份批准版本和原件摘要可核对。 |
| 研究。四个独立问题仅三个有证据，第三方处理一个问题后断线，通知再重复到达。 | 比较 Hermes 的子结果校验／投递状态、Manus 的任务事件及 Kimi 的分支展示。 | 四个对象均有明确处置，缺证问题可解释；恢复只查原任务，无重复派发。结果已产出、提醒失败分别记账。 |
| 售后。客户发来两单诉求后补一张图片，平台要求补证；群消息被重复投递。交客户回复和平台证据包。 | OpenClaw 的渠道绑定和 QwenPaw 的消息基线检验事件归属；用 Muse 的持续委托参照检查提醒权何时结束。 | 两个事项正确拆分，图片只关联一项，草稿按收件对象裁剪；没有外发、退款或平台裁决。与采购共用提取、对象匹配、取证、起草和审核。 |

**可比较的实验。** 同一资料集、已冻结业务答案和预算下，比较固定流程、有限工具回合和独立对象并行三条路径。可控制模型时固定模型修订；商业产品只能记录可见模式、套餐和设置，不能把产品差异归因为某一种 harness。每次保存输入、合法资料范围、输出文件、人工接手点、完整耗时和可见用量；按约定同时报告已解决对象数、错误完成、重复动作和每份合格交付成本。未披露费用记未知。人工只处理预设缺口，审核人依据同一标准并独立核查原件。

**采用顺序。** 先把任务完成、内容达标、用户采纳、提醒送达分开，以一份交付清单贯通内置、外接、自建三条路径。随后验证无进展检测、外部回执核对与跨端待办。跨期监听、通用电脑操作、真实外部写入只在有资源授权和单独验收边界时再决定。具体设计见产品第 27 节、技术第 21 节与交互方案「任务接续、能力接入与构建」。

### 三个底层机制

**OpenClaw 如何处理等待。** 一个长驻 Gateway 连接多种消息渠道，执行循环把工具事件、会话和运行关联起来。调用方等待超时后，底层 Agent 仍可能运行。主会话工具默认可在主机执行，隔离取决于部署配置。对 Alliance，最直接的借鉴是在超时界面提供原运行入口和最后活动时间，随后查询原运行。网关能接通多个渠道也意味着每次恢复需要重新核对操作者的身份。[网关架构](https://docs.openclaw.ai/architecture) · [执行循环](https://docs.openclaw.ai/concepts/agent-loop) · [部署边界](https://github.com/openclaw/openclaw/blob/6e113fecbf30fdc33caae336139dc785b6dc1489/README.md#security)

**Hermes 如何复用经验。** 它可以从复杂任务提炼技能，定时作业可绑定一个或多个技能。每次定时执行创建新会话，可加载持久记忆，但不会自动带入上次作业的对话。系统还能配置记忆或技能写入的审阅。对周期报告而言，应分别保存固定口径、上次处理的数据位置和个人偏好，才能避免凭对话记忆漏读或重复处理资料。[项目说明](https://github.com/NousResearch/hermes-agent/blob/2de9f51b8008a7d49a49221c184f2f11cbfc4af1/README.md) · [定时运行上下文](https://hermes-agent.nousresearch.com/docs/developer-guide/cron-internals) · [写入审阅](https://hermes-agent.nousresearch.com/docs/reference/slash-commands)

**OpenManus 如何停止。** 固定版本的通用 Agent 将默认上限设为 20 步，配有 Python、文件编辑、向人提问和结束工具，也可连接浏览器 MCP。基类逐步执行，检测到重复响应会提示变更策略，到达上限会产生终止说明。这里能清楚看到需由产品补上的判断：达到步数上限时，即使循环顺利退出，用户的成果仍可能缺失。[通用 Agent 源码](https://github.com/FoundationAgents/OpenManus/blob/3309bf4e416fb1c74b008f3e86494439a31bad53/app/agent/manus.py) · [循环与停止逻辑](https://github.com/FoundationAgents/OpenManus/blob/3309bf4e416fb1c74b008f3e86494439a31bad53/app/agent/base.py)

## 附录 B　个人工作区如何支持执行

**nanobot 把中间动作放进工作区。** 用户能为一个话题选择项目目录和访问方式，展开工具调用、文件修改差异与用量，必要时从较早的回复分叉。周期报告和本地事件触发器有独立管理入口。它提供了一个低成本的交互参照：处理销售表时，用户可以直接核对 Agent 打开了哪个版本、改了哪些单元格，再决定是否继续。分叉会话和回滚外部业务操作是两项不同的工程能力。[固定版本工作区说明](https://github.com/HKUDS/nanobot/blob/db0306b404954e48ffb82ceae70cbf6f73094348/README.md#-webui)

**CowAgent 将工作经验带回下一次任务。** 渠道把消息交给核心 Agent，后者结合可用工具、技能、记忆与知识规划和执行，再从原渠道返回。短期会话、按日记忆和长期记忆分层，主题知识另行组织。多个 Agent 可以在共享对话中协作，各自持有工作区和知识。Alliance 可借鉴这种区分：用户说“以后金额显示两位小数”适合存为可编辑偏好；“这次财务已核准这份清单”应保留为有版本的项目证据，且只在相应项目使用。[架构及记忆分层](https://github.com/zhayujie/CowAgent/blob/51ffe5a8df75295a5c063d5bc32a055c643a2599/README.md) · [团队协作](https://docs.cowagent.ai/multi-agent/team)

**QwenPaw 把文件检查点与工具策略放在同一工作环境。** 项目记录了工作区检查点、文件差异、运行时子 Agent、浏览器和桌面操作，并提供按能力调用允许、拒绝或请求批准的策略。它支持从钉钉、飞书、微信等渠道进入同一实例。用于企业工作流时，可以向用户展示可恢复的文件版本，同时单列邮件发送、远端记录修改等已发生的外部动作。恢复文件版本不能收回送达的消息。[固定版本能力与安全说明](https://github.com/agentscope-ai/QwenPaw/blob/b02e17b8cf3fdde484f33c6981321280a0417232/README.md) · [项目安全文档](https://github.com/agentscope-ai/QwenPaw/blob/b02e17b8cf3fdde484f33c6981321280a0417232/README.md#security)

### 开源实现的取舍

| 设计问题 | 优先阅读的项目 | 对 Alliance 的具体启发 |
| --- | --- | --- |
| 一个对话如何容纳多个在途任务 | OpenClaw、nanobot | 消息关联原运行，支持查看、补充与取消，区分等待超时和运行终止 |
| 一次任务如何调整路径 | OpenManus | 每步观察工具结果，记录退出原因，设动作、耗时和费用上限 |
| 如何让下周的任务记得这周的经验 | Hermes、CowAgent | 偏好、可执行技能、上次处理位置分别保存，允许用户修订 |
| 如何让用户知道工作区发生了什么 | nanobot、QwenPaw | 交付时给差异和版本，接管时显示最近动作及尚未提交的内容 |
| 有多个执行者时如何划清责任 | Hermes、QwenPaw、CowAgent | 子任务显式分配工具、输入、费用和结果归属，收回授权后复查 |

选型时最容易高估的是“支持某个工具”这一项。文件能写入、内容正确、用户批准该版本，是三个需要分别取证的事实。开源文档对机制的可见性，给了我们设计验证用例的依据；跨设备恢复率、任务完成质量和真实使用成本仍需同题实测。

## 附录 D　商业产品如何交付和持续跟进

**Kimi Agent 以可下载的成果承接长任务。** 用户可以离开页面，任务在后台继续。普通模式通常一次输出一个文件；Swarm 可将多对象调研分给多个子 Agent，展示各分支进度并汇总为表格、文档或文件夹。官方提示，长对话改稿可能遗忘早期细节，Swarm 的消耗也可能达到普通任务的数倍。对 Alliance，多文件交付适合先冻结必交清单，最终按清单逐项核对，对缺失项指定重做范围。[功能与输出限制](https://www.kimi.com/en/help/agent/agent-features-and-limits) · [Swarm 与会员可用性](https://www.kimi.com/en/help/agent/agent-swarm) · [共享额度规则](https://www.kimi.com/en/help/agent/agent-quota-and-billing)

### 同一项个人委托的四处差异

| 在任务中的时刻 | 样本给出的做法 | 我们需要保存的事实 |
| --- | --- | --- |
| 用户关闭电脑 | Work 使用独立云浏览器；Cowork 云端持续运行，本机文件受设备状态限制 | 运行位置、资源位置、最近可达时间、是否可改用已授权副本 |
| 用户说“继续” | Manus 的确认对应某个事件；Work 可以把网页交还用户操作 | 待确认动作、目标对象、预期效果、参数版本、责任人和有效期 |

| 任务下周再做 | Hermes 的周期任务创建新会话；ChatGPT 的共享任务副本使用接收者自己的权限 | 指令版本、时区、数据游标、本次身份、去重键和通知条件 |

| 制定及调整计划 | 可查看依赖，缺一份资料时先推进独立部分 | 方案版本、依赖、变更原因、影响范围 |
| 选择工具与执行位置 | 优先调用获准的数据接口，必要时使用指定工作区或浏览器 | 工具修订、所需权限、设备状态、执行环境 |
| 根据观察继续行动 | 读到列名变化后请求映射，工具报错后选择允许的下一步 | 工具输入摘要、结果类型、已尝试路径、剩余额度 |
| 处理中断与接管 | 用户只补缺失项，返回后沿用同一任务 | 阻塞原因、待处理事件、当前处理人、恢复点 |
| 控制外部副作用 | 草稿可修改，正式发送前展示对象及内容，重复点击仅处理一次 | 动作键、参数摘要、提交意图、回执或核对结果 |
| 使用记忆与技能 | 个人偏好可更正，一次性项目资料按授权取用，旧技能可回退 | 所属范围、来源、版本、过期与撤销状态 |
| 分派并行任务 | 逐项呈现覆盖范围，缺失项目可以单独补做 | 子任务输入、份额、工具范围、结果来源 |
| 验证与交付 | 可下载文件，查看总额怎样算出、谁确认了哪个版本 | 业务断言、重算结果、文件版本、审核与交付记录 |
| 持续运行与通知 | 定时或事件触发，只有命中条件或需要人处理时才提醒 | 触发原因、上次处理位置、重入策略、通知去重 |
| 成本与可观测性 | 能解释一次交付花了多少、时间耗在哪一步 | 调用和设备耗时、等待耗时、预占／结算、脱敏事件 |

**贯穿示例。** 收到“出本周销售表”后，先冻结日期范围和资料版本，读取核准字段并用计算工具聚合。若缺少币种，保留已解析的数据并向负责人提一个具体问题。补充后继续计算，用独立求和检查工作簿合计，再把带来源版本的 XLSX 送审。如果本次仅授权生成文件，到此即可交付。后续请求发送时，系统展示收件人与附件版本；若发送接口超时，先核对该次提交的回执。

这个例子也给出了自主性的边界。模型可以重新安排已授权的读取和计算；变更数据范围、收件人、外部系统或预算时，必须让相关负责人看到变化。工作进度、人的授权和外部世界已发生的事实应保留在可查询的记录中。

现有核心路径是先解析绑定的资源和修订、检查授权及预算、写入提交意图，再调用模型、工具或外部 Agent 并提交结果。新设计可在这条路径内加一种能够继续观察和行动的步骤；若把整个模型循环藏进一次活动调用，Worker 重启后就难以判断其中哪些动作实际发生，预算也看不到真实扇出。[运行与调度](../backend/internal/runtime/runtime.go) · [外部任务核对](../backend/internal/runtime/remote.go) · [工具实现](../connectors/server.py) · [重建清单](15-rebuild.md)

### 一个可实现的执行约定

**发起。** 父步骤保存目标、输入版本、必交成果、可用工具和授权上限。模型每轮只提出下一项动作及理由摘要；运行时校验身份、参数、费用、时间和步数，将通过校验的动作与父步骤关联。重试同一次意图沿用动作键，新参数或明确的新动作使用新键。

**观察。** 每次调用结束，工具返回可区分的结果，包括成功并附回执、输入可修正、缺权限、需人工登录、暂时不可用、外部结果未知。只读动作可限次重试。外部写入若结果未知，先读回目标状态或查询原回执；无法核实时挂起，显示核对责任人。取消运行时分别记录本地停止与远端实际结果。

**退出。** 只有完成该步骤的业务检查才将成果送审。步数耗尽、预算不足、重复无进展、用户取消、授权撤销分别保留退出原因。被阻塞的子项保留输入与中间结果；恢复时复查权限、资料版本和剩余额度，再从最近一个已确认的动作继续。成果送审和最终交付沿用现有审核职责。

### 建议首批基准任务

| 任务与干扰条件 | 通过条件 |
| --- | --- |
| ① 销售汇总。给含未核准行、负数、重复名称及两位小数的 CSV | 筛选及分组正确，独立重算总额与 XLSX 一致，绑定输入版本 |
| ② 输入不全。缺币种或关键列，用户随后补充 | 明确指出缺项，补充后沿用原任务；原始资料及映射决定均可核对 |
| ③ 中途重启。分别在调用前、外部提交后但回执落库前停止 Worker | 已确认结果可复用，未知结果进入核对，有效外部写入至多一次 |
| ④ 人工接管。等待登录时撤销授权，随后从旧链接点击继续 | 原授权失效，显示原因；只有经过当前授权校验才可执行下一步 |
| ⑤ 批量调研。十个对象中一个失败，另一个缺来源 | 总表列出十个对象和缺口；可以只补做两项，来源与对象一一对应 |
| ⑥ 周期委托。同一周期重复触发，且上期数据迟到 | 每一周期有独立运行，重复触发可去重，迟到数据按预设口径处理 |
| ⑦ 预算与交付。运行中耗尽额度，恢复后用户改稿 | 追加后复用已成功动作，只结算实际调用；最终包与批准版本一致 |

**评估设计。** 现有固定方案作为基线，新增步骤循环作为候选。绑定同一模型修订、输入、工具、预算和标准答案；正常样例与上述干扰样例分别计数，每例至少重复 3 次并报告样本数。先用可控工具验证状态转换和边界，再使用获准的真实模型、真实只读业务连接器复测任务质量。现有公开 A2A 证据覆盖文本问候，合成故障验证覆盖多种恢复路径，不能据此推断商业服务上的完成率。[当前验收边界](15-rebuild.md) · [公开 A2A 证据](evidence/rebuild-public-hello/public-agent.json)

**核心指标。** 同时报业务完成率（通过全部必验项／发起任务）、无需人工纠错完成率、正确恢复率（恢复后通过且无重复副作用／注入中断的任务）、每个成功交付的总成本（含失败轮次），以及耗时中位数和 P95。把业务要求的审批与因错误造成的返工分别计数，将等待人的时长单列。首轮样本较小时附每次耗时和失败原因。越权外发、重复提交和错误版本交付在首批用例中出现一次即停止扩面；其余阈值在拿到基线后确定。

**下一轮设计评审应形成三个决定。** 先选哪一个业务任务作为标杆；列出该任务允许自动执行和必须交人的动作；写出足以确认完成的机器检查与人工检查。建议从已有销售汇总与 XLSX 交付开始，第一次评审直接使用现成样例、预期金额、文件原件和故障回执，逐项讨论 Agent 可以把工作推进到哪里。
