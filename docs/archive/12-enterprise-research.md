# 企业 AI 助手落地：背景、场景与产品调研

调研日期：2026年11月15日。本文服务于 [产品方案 v32](10-product-blueprint.md) 的定位复核；不新增已实现功能，不启动开发。

方法：检索并阅读机构研究、官方产品文档、项目仓库和许可说明。市场调查用于判断问题与提出假设，产品文档用于核对功能声明；二者均不替代目标客户访谈、安装验证和真实业务验收。本轮未开展客户访谈、第三方部署测试或付费模型测试。公开仓库的维护和许可情况为查询时快照，采用具体版本前仍需复核。

## 1 结论与证据边界

项目定位明确为：**面向缺少专门开发能力的企业及业务团队，交付可直接使用、简单定制、持续更新并可协作管理的 AI 助手平台。** 普通成员通过助手完成日常工作；维护者配置可复用能力；管理者查看业务采用、运行质量、消耗、成本及获授权的 Trace。

这是本项目的产品选择，不将“AI 一定先从企业落地”写成已证实的市场规律。消费端也存在大量实际使用，OpenAI 的消费者 ChatGPT 使用研究覆盖工作及非工作用途；其样本不能代表企业产品市场。我们应论证的是企业中的具体需求与产品机会，而非否定个人 Agent。[研究说明，2025年9月](https://openai.com/index/how-people-are-using-chatgpt/)

本轮推论是：企业需要的不仅是构建 Agent 的工具，还需要有人承担集成、授权配置引导、验证、更新和故障处理。产品竞争力应通过“无开发人员能否完成首次工作、多人能否可靠交接、结果是否可用、后续是否可维护”验证，不能只统计接入数量。

尚缺中国目标企业的一手证据：现有软件、数据权限质量、实际预算、购买与部署决策、员工接受程度、需要的专业成果深度。以上研究不能替代这些问题。

## 3 目标用户与痛点假设

以下是研究结合项目方向形成的产品假设，不是假装已经完成的用户访谈。

| 角色 / 工作障碍 | 产品响应 | 应取得的验证证据 |
| --- | --- | --- |
| 普通员工知道业务目标，不知道选模型和工具 | 默认助手、场景入口、自然语言追问、资料上传，能力细节按需展开 | 未接受开发培训的用户独立完成真实任务，记录阻塞点 |
| 业务骨干反复提供规范、模板和品牌资料 | 在授权范围内形成助手配置、知识与可复用方法 | 第二次任务能复用，同时不会沿用失效资料 |
| 发起人需要多位同事和 Agent 配合 | 一份共享任务、人员分工、资料补充、局部反馈、明确最终确认 | 交接、意见冲突、人员缺席和版本并发仍可完成 |
| 管理者不知道谁在使用、结果如何、钱花在哪 | 业务采用与交付、质量阻塞、消耗费用、按权限下钻 Trace | 汇总可以追溯到运行；失败、未知费用、待审核不被隐藏 |
| 维护者会配置但不会搭技术栈 | 平台负责打包集成，企业按引导填写资源、授权、知识和规则 | 无需克隆仓库、写适配代码即可启用首发能力 |
| 账号和数据分散，连接成功但用不了 | 区分资源连通、Agent 可用、协作通过；按实际授权判断 | 使用不同身份验证数据范围及撤权，不能只测试管理员账号 |
| 现有能力失效或升级破坏定制 | 可见维护状态、依赖影响、配置差异、验证与升级记录 | 验证正常升级、保留定制、失败恢复和旧任务隔离 |
| 认为模型回答即可交付，却缺少证据 | 来源、成果操作能力、明确采纳、版本与交付记录 | 输出有用性由业务审核人确认，模型评分不替代采纳 |

首批客户优先选择哪类企业、部门、人数与管理层级仍待讨论。“无开发能力”也需区分无开发人员但有管理员、依靠服务商运维，以及完全无技术支持三种情况；它们对应不同交付方案。

## 4 跨场景工作与多人协作

以下为待验证的通用场景库。用来发现共性及能力缺口，不把每一行自动加入第一期验收承诺；已确认的三主场景与专业扩展仍按 D17 执行。

| 场景 | 输入与可组合能力 | 人的协作及交付 | 首期边界与成功信号 |
| --- | --- | --- | --- |
| 日常知识问答 | 已授权制度、项目资料；检索、引用、归纳 | 员工提问，知识负责人修正；带依据的答案 | 不跨权限回答；简单任务明确采纳，可报告无答案 |
| 会议整理 | 用户提供的纪要或转写；摘要、事项提取 | 参会者核对责任与日期；纪要及行动建议 | 不假定已具备实时录音、转写或自动建正式任务能力 |
| 销售方案及投标准备 | 客户需求、产品资料、格式模板；研究、写作、表格、文档 | 销售协调产品和交付人员核对；方案草稿及证据 | 不编造报价、承诺或资质，不自动提交或修改 CRM |
| 经营周报 | 授权导出表格、口径；受控计算、解释、图表、文档 | 数据负责人核对口径，管理者确认；周报 | 可复核计算，区分事实和建议；不改变正式经营数据 |
| 客服知识与回复草稿 | 工单副本、产品文档；检索、分类、写作 | 客服校核，疑难交业务负责人；回复与知识修订建议 | 不向外部客户自动发送，不擅自退款或变更工单 |
| 新品发布材料 | 产品依据、品牌规范；研究、文案、视觉、文档和检查 | 产品核事实、设计核视觉、市场最终确认；素材包 | 不上架投放；修改卖点时核对关联成果 |
| 市场研究 | 公开来源及自有资料；搜索、引用、计算、写作 | 研究者核证据，决策者评估建议；报告和数据附录 | 证据可追溯，不把网页说法当已核实事实 |
| 培训与入职资料 | 角色规范、知识、模板；检索、写作、课件制作 | 业务专家与培训负责人共同审核；课件与练习 | 知识可维护，不依赖自动公开发布 |
| 采购比较 | 用户提供的供应商材料、指标；提取、计算、对比 | 使用部门核需求、采购核条件；比较表与问题单 | 不下单、不改变供应商记录、不作未经核实的确定承诺 |
| 人事与财务资料整理 | 获授权政策或单据副本；提取、归类、校核 | 对应负责人审核；资料清单和待核对项 | 不作人员录用淘汰决定、付款、报销批准或账务写入；敏感数据授权另行验证 |

共用结构是：业务目标、资料与依据、助手及协作分工、人员责任、成果版本、反馈、确认和使用记录。单次问答采用轻量呈现，复杂工作才展开项目方案。通用不等于所有工业控制、医疗决策、金融交易或专业编辑能力都已具备。

## 6 “尽可能多内置”的可执行解释

**已确定方向**：持续扩充公开工具、连接器、Agent 和业务模板；由项目发布版本供企业升级。不能把现有六类默认 Agent 当作最终能力上限。

**建议的交付层次，待确认**：

| 层次 | 企业看到什么 | 平台承担什么 |
| --- | --- | --- |
| 随版本交付的基础能力 | 完成必要资源配置后即可使用的助手与模板 | 固定版本、集成、测试、说明、维护责任与升级路径 |
| 按需启用的能力包 | 场景、所需账号、授权、费用、支持的成果操作 | 准备适配及依赖；安装方式随部署形态确定，不要求业务人员写代码 |
| 可发现的生态候选 | 来源、维护状态、待验证项、接入申请 | 标明未纳入支持范围，不能显示为直接可用 |
| 团队专用定制 | 用描述、资料、规则和组合形成草稿 | 试运行、版本、共享发布；不覆盖原始基线，也不越权调用新资源 |

能力扩充优先按日常业务覆盖和复用价值，而非项目热度：资料理解与知识、公开研究、内容与视觉、表格分析、文档课件、协作信息读取、受控成果制作、外部专业 Agent。已确认百炼默认、方舟替换验证、DeepSeek 文本补充，以及轻量检索、DuckDB、受限表达式、原生/PDF.js/LibreOffice 预览不变；新增组件属于候选，须补矩阵及证据。

目录里的每项建议展示用途、输入成果与修改深度、支持范围、来源和许可、版本与依赖、数据流向、授权与费用、验证证据、负责人、可用及维护状态。发现、随产品分发、安装、资源连通、Agent 可用、团队发布是不同事实，不用一个“已接入”状态覆盖全部。

模型仍优先由团队提供云资源、团队承担费用，每个 Agent 独立绑定凭据引用。开箱即用承诺的是平台已做好集成和引导，不承诺免费模型、不需要业务数据授权，或任意外部 Agent 零配置可用。

## 7 持续更新与管理者视角

持续更新是已明确的产品责任；下列实施流程为待讨论建议：

1. 平台发行方维护能力目录，核对来源、许可、维护状态、兼容性、授权变化及验证结果，生成可审阅的版本说明。
2. 企业看到本次新增、修复、停用风险、依赖和权限变化；产品升级、能力包升级、企业配置修改分别呈现。
3. 在可验证的环境测试升级，列出定制冲突和需要重新授权或复验的部分，再由有权人员启用。具体托管或本地升级方式尚未决定。
4. 旧任务继续按已受理版本及当前有效权限处理；不静默切换模型、工具或 Agent。回滚只对明确支持的部分承诺，数据迁移及远端副作用不能假装自动撤销。
5. 上游停止维护时说明影响、停止新增风险范围或提供替代，按现有普通停用、紧急停止与迁移规则执行。

管理者应能看到：助手使用和业务覆盖、任务交付及等待、失败重试、质量反馈、费用消耗、能力健康，并能在权限范围内下钻 Trace。既有项目最终确认、资源授权和管理身份继续分开；拥有管理入口不自动获得全部员工对话、原始文件、凭据或业务验收权。

**待确认指标口径**：活跃用户与任务采用数、经过确认的完成数、返工率与原因、等待时间、每次已确认交付的可归属成本。节省工时需要基线和人工抽样，不用 token 数推算生产力；自报满意度、执行成功率和业务采纳率分别统计。部门粒度、个人明细、敏感 Trace 内容访问及导出授权需明确后才能实现。

## 8 待讨论事项与调研下一步

产品中的统一清单见 [第22节](10-product-blueprint.md#22-企业落地定位与产品边界复核)。优先讨论：

1. **P0 交付与运维责任**：托管、企业自部署或服务商交付如何取舍？无开发能力的企业由谁完成安装、备份和升级？
2. **P0 首批客户与组织范围**：目标企业/部门、人员规模、是否有管理员、既有协作与知识系统；企业、团队、部门的映射。
3. **P0 首发能力包与承诺深度**：基础默认组合、第一批连接器和外部 Agent、哪些只列候选；能够以业务配置完成的定制边界。
4. **P0 管理者视图与授权**：成本质量管理范围、是否允许看个人细节、Trace 正文及对话可见范围。
5. **P1 更新机制与定制保护**：版本频率、安装渠道、离线要求、许可分发、维护周期、验证和回退范围。
6. **P1 采用与质量指标**：选取企业真实任务，建立人工基线及成功定义；授权和知识更新如何持续维护。

建议接下来访谈少量目标企业的业务用户、管理者及实际运维负责人，并观察一次完整工作：现状输入输出、交接与返工、所需账号、真实数据权限和购买约束。样本数及对象待定，不将桌面研究包装成需求已验证。先验证首次价值和持续使用，再扩大目录；所有候选与测试仍按 Mock、真实集成、真实能力分别报告。

## 9 对现有方案的影响

- 产品开头、第2、3、5、11—15节及第22节：企业定位、普通用户和管理者、助手与能力包、日常任务、协作和验收。
- 第19—21节：保留已确认资源和29项配置矩阵；明确平台集成与企业配置的责任，不要求普通员工组装技术组件。
- D01—D17：保留内部团队、审核权限、资料版本、费用、停止恢复和验收原则；微信仍不在本期接入。
- 技术方案：保留已确认骨架及接口时序；部署、包更新、组织权限和管理视图需承接本轮产品结论。Temporal/Eino 检查点与统一调用细节仍属待确认建议，暂不向实现推进。
